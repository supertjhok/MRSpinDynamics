# MRSpinDynamics v0.3.0 release plan

_Audit date: 2026-07-12_

## Release intent

Version 0.3.0 should be a stabilization and workplace-readiness release. The
scientific scope accumulated since v0.2.0 is already large enough. Work before
the tag should improve installation, performance predictability, documentation,
release artifacts, and cross-project operation rather than add another physics
feature family.

The workspace remains one citable release: one version across
PythonSpinDynamics, QuadrupolarDFT, and `mr-integration`, one Git tag, one GitHub
Release, and one Zenodo archive.

## Audit findings

### P0: complete before a release candidate

1. **Ship the Python package license text.** The Python wheel and sdist build and
   pass Twine, but neither currently contains a GPL license file. Copy the root
   license into `PythonSpinDynamics/` (as already done for QuadrupolarDFT and
   integration), declare/verify license-file inclusion, and make the installed
   distribution test fail when it is absent.
2. **Expose the installed version.** Add `spin_dynamics.__version__`, a
   `spin-dynamics --version` option, and the PythonSpinDynamics distribution
   version to saved-run environment provenance. Test editable and wheel installs.
3. **Publish useful workspace artifacts.** Extend the tag workflow to build and
   attach checked Python wheel/sdist artifacts, the three user-manual PDFs, and
   a SHA-256 checksum file. If all three wheels are attached, document their
   workspace/offline installation order because the integration wheel depends on
   the two subproject distributions.
4. **Make documentation artifacts current.** Regenerate and visually inspect all
   committed manuals, API reference, and validation matrix from the release
   commit. The stale Python manual identified above must not reach the tag.
5. **Finalize release metadata.** Fix changelog comparison links, move the drafted
   Unreleased material to `[0.3.0] - YYYY-MM-DD`, bump all workspace versions and
   `CITATION.cff` together, and confirm `scripts/extract_changelog.py 0.3.0`.
6. **Require green release-commit CI.** Workspace and integration CI are green for
   the current audit commit; PythonSpinDynamics CI was still running when this
   document was drafted. Do not tag until every required workflow is green on
   the exact release commit.

### P1: worthwhile stabilization before v0.3.0

1. **Control numerical-library threads in tests and process workloads.** A broad
   Windows validation run hit a native access violation with unrestricted BLAS
   threads and passed all 243 impacted tests when `OPENBLAS_NUM_THREADS`,
   `OMP_NUM_THREADS`, and `MKL_NUM_THREADS` were set to one. Set deterministic
   thread limits in CI/release tests and document how they interact with powder
   process workers to avoid oversubscription.
2. **Extend performance coverage.** The host-normalized gate covers four compact
   legacy workloads but not the new powder-waveform path. Add a compact
   reduce-only powder case. Also give benchmark schemas an explicit version or
   a stable common subset: the current gate cannot compare HEAD directly with
   v0.2.0 because some benchmark cases did not exist in that release.
3. **Test the declared minimum dependency floor.** Normal CI installs current
   dependencies. Add one Python 3.10 lane using the documented minimum NumPy,
   SciPy, and Matplotlib versions so `numpy>=1.24` remains an evidenced claim.
4. **Add one full Windows release lane.** The Windows matrix currently runs the
   smoke tier only. A single Python 3.12 full-validation lane with controlled
   numerical threads would catch platform-specific process/spawn and native
   library failures without multiplying the whole matrix.
5. **Improve package metadata.** Add project URLs (source, documentation, issues,
   changelog) to the three `pyproject.toml` files and test them in artifact
   metadata. Keep PythonSpinDynamics classified Alpha for a workspace release;
   do not imply PyPI/API stability that the known-gaps document does not claim.
6. **Add a release preflight command.** One script should check version agreement,
   changelog extraction, clean generated API/validation files, manual existence,
   distribution builds, license inclusion, Twine metadata, installed CLI/version,
   and checksums. The tag workflow should call the same script where practical.
7. **Clarify offline/workplace installation.** Document installation from the
   GitHub Release bundle and a tested three-wheel `--find-links` workflow. This
   is more appropriate for v0.3.0 than starting public PyPI publication.
8. **Make release scripts UTF-8-safe on Windows.** Changelog extraction succeeds
   with `PYTHONUTF8=1` but the current command can fail under a CP-1252 console
   when older release notes contain isotope superscripts. Configure UTF-8 output
   inside the script or provide a byte-safe output path and add a Windows test.

### P2: explicitly defer

- more facade routes or new physics engines;
- broad static-typing expansion beyond the current typed boundary;
- raising the coverage floor solely for the release number;
- public PyPI/TestPyPI publication and hosted documentation;
- sparse/Krylov or GPU implementations that change numerical architecture;
- further scientific examples unless required to repair a release-blocking
  usability or correctness issue.

## Proposed work sequence

As of 2026-07-12, Phases A and B have been implemented and are undergoing the
Phase C validation pass. Version finalization and tagging remain deliberately
deferred until that pass is green.

### Phase A: release hygiene

- Commit the current Python manual PDF and root `tmp/` ignore rule.
- Complete the v0.3.0 changelog draft and this plan.
- Add the PythonSpinDynamics license copy and artifact-content assertion.
- Add package/CLI version reporting and project URLs.

### Phase B: release automation and performance guardrails

- Add deterministic BLAS thread settings to relevant CI jobs.
- Add the compact powder performance case and benchmark schema handling.
- Add the minimum-dependency and full-Windows release lanes.
- Extend the release workflow to build manuals/distributions and publish
  checksummed artifacts.
- Add the release preflight script and offline-install documentation.

### Phase C: release-candidate validation

Run from a clean checkout of the proposed release commit:

1. workspace version/changelog checks;
2. Python smoke, Ruff, generated API/validation checks, MyPy, branch coverage,
   optional Numba/JAX parity, and performance regression;
3. full Windows validation with numerical threads fixed at one;
4. QuadrupolarDFT tests and manual build;
5. NQRDatabase export/audit workflows;
6. cross-project integration tests and examples on Python 3.10 and 3.12;
7. all wheel/sdist builds, Twine checks, clean isolated installs, CLI/version
   checks, license checks, and offline three-wheel installation;
8. two-pass manual builds and visual inspection of changed pages;
9. live confirmation that every required GitHub Actions workflow is green.

### Phase D: cut v0.3.0

1. Freeze feature work.
2. Run `python scripts/bump_version.py 0.3.0 --date YYYY-MM-DD`.
3. Move the changelog draft to `## [0.3.0] - YYYY-MM-DD` and create a fresh,
   empty Unreleased section.
4. Regenerate and commit all release artifacts.
5. Run the preflight from a clean checkout and push the release commit.
6. Wait for green CI on that exact commit.
7. Create and push annotated tag `v0.3.0`.
8. Verify the GitHub Release body, downloadable artifacts/checksums, and Zenodo
   archive; add the version DOI in a follow-up metadata commit if required.

## Release acceptance criteria

- The working tree is clean except ignored local environments/caches.
- All four version declarations and the tag equal `0.3.0`.
- `scripts/extract_changelog.py 0.3.0` produces complete release notes.
- Every required CI workflow is green on the tagged commit.
- The Python wheel and sdist contain GPL license text, `py.typed`, the console
  entry point, correct version, and project URLs.
- A clean workplace machine can install the documented artifact bundle and run
  `spin-dynamics --version`, `spin-dynamics --help`, and the installed
  distribution verifier without using the source tree.
- Committed manuals match their sources and open without rendering defects.
- Release artifacts have published SHA-256 checksums.
- No known issue in the release notes is disguised as a validated capability.
